1.6  API surface

Three protocols, chosen per consumer rather than per fashion. REST/JSON for operator and partner integrations (cacheable, debuggable, easy to document). gRPC for internal service-to-service and the edge gateway (typed, streaming, low overhead on a marginal restaurant uplink). WebSocket for guest-facing live state. GraphQL is deliberately excluded from the transaction path — it makes rate limiting, caching, and cost attribution materially harder for a system whose core endpoints are a small, stable set.

Public API v1. All mutating endpoints require Idempotency-Key; all responses carry X-MD-Request-Id. Auth is OAuth2 client-credentials for partners, OIDC for humans, device-bound mTLS certs for terminals.

1.7  POS integration logic

Two distinct modes, and conflating them is the classic failure. Native mode: Mobile Dinners is the POS and owns the menu of record. Coexist mode: an incumbent POS (Toast, Square, Clover, Revel) remains the system of record and Mobile Dinners operates as a growth and demand layer on top. Coexist is the wedge that lets a restaurant adopt without ripping out hardware mid-season; native is where the margin and the data quality live. The migration path between them is a product feature, not an afterthought.

1.8  Offline-first gateway protocol

The gateway is a small Linux appliance (or a designated terminal acting as leader) that holds a full local replica of the location's operating data and continues to run a complete service window with zero internet. This is the hardest engineering problem in Plane A and the one that earns trust with operators — a POS that dies with the Wi-Fi is a liability, not a product.

  Clock: hybrid logical clocks (HLC) on every local write. Device wall-clock is
  untrusted; `occurred_at` is kept for forensics, `recorded_at` + HLC order events.

  Retention: 14 days local, then pruned once cloud-acked.
  Crypto: local DB encrypted at rest; outbox signed with the device key so a
          tampered appliance cannot forge orders into the cloud.
Risk control — store-and-forward payments

Offline card acceptance transfers chargeback risk to whoever authorizes it. Policy: an offline floor limit (default $75), a per-window aggregate cap (default $2,000), a hard cutoff at 4 hours offline, and a per-tenant opt-in with the risk stated in plain language during onboarding. Above the cap, the terminal requires cash or a signed intent to re-run later. Do not let a growth-hacking instinct set these defaults; let the risk team set them.

1.9  Marketplace and dispatch logic

The marketplace has to solve three problems simultaneously: what to show (ranking), whether it can actually be made (capacity), and whether it can be delivered on time (dispatch feasibility). Most consumer food apps solve the first and fake the other two. Because Mobile Dinners owns the kitchen, it can be honest.

     ├─ collaborative filtering  : ALS/two-tower ANN over person embedding
     ├─ content similarity       : pgvector kNN on item + cuisine embeddings

     ├─ repeat-affinity          : this person's own reorder set
     └─ new/cold-start           : editorially boosted, exploration budget

  Stage 3 — RANK  (~60ms, gradient-boosted ranker → LambdaMART/XGBoost)
     score = w1·P(click)          learned

           + w3·expected_margin   ← restaurant's margin, NOT platform take
           + w4·fulfillment_conf  ← P(on-time) from prep + dispatch model

     diversity (max 2 per cuisine in top 10) · dedupe brands ·
     ε-greedy exploration slot (ε = 0.08) · sponsored slot at rank 3 or 7,
     always labeled, never blended, and suppressed if relevance < floor

  DELIVERY QUOTE  (the number the guest is promised)
  ──────────────────────────────────────────────────────────────────────────
    promised_at = order_time

                + courier_to_store_eta
                + drive_time(store→guest, live traffic)

    Quote the p80, not the mean. Underpromising by 4 minutes costs
    nothing; overpromising by 4 minutes costs a refund and a review.

  ──────────────────────────────────────────────────────────────────────────
  DISPATCH  (offer → accept → batch)
  ──────────────────────────────────────────────────────────────────────────
    Assignment is a rolling-horizon bipartite match re-solved every 10s:
      minimize  Σ (courier_wait + guest_lateness·λ + empty_miles·μ)
      s.t.      one active offer per courier
                batch_size ≤ 3 and detour ≤ 8 min and no cold-item mixing
                (hot ∥ frozen never batched)

    Supply ladder, in priority order:
      1. Restaurant staff driver (cheapest, best margin for operator)
      2. Mobile Dinners gig pool (metro-dependent, density-gated)
      3. Third-party courier network (Nash / Uber Direct / DoorDash Drive)
      4. Pickup-only fallback — if no supply, do not show a delivery
         promise the network cannot keep. Degrade the offer, not the truth.
